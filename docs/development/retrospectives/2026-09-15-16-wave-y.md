## 改善が必要なこと

### 1. 同じ形の欠陥が 4 設計連続で出るまで止められなかった

**影響: PR #2251 を丸ごと破棄。3 サイクル分の実装・レビュー・CI を失った。**

#2249（ハンク本体の `+++` 行をヘッダと誤認する）の修正で、次が起きた。

| 設計 | 内容                                        | 結果                                                                     |
| ---- | ------------------------------------------- | ------------------------------------------------------------------------ |
| 1    | `inHunk` boolean、`diff --git` でのみ reset | **D1**: 非 git unified diff で 2 本目以降が silent drop                  |
| 2    | 終端 2 系統（前置無し行 / `@@` の行数予算） | **D2**: overstate × 非 git で drop ／ **D3**: understate で hints に幽霊 |
| 3    | D3 対策に `+++` の pair 要求を追加          | **D4**: understate × 偽装 `--- `/`+++ ` PAIR で幽霊が復活                |

3 回とも **「ハンク終端の判定を足す → その終端が誤作動する帯域で header 判定が復活する」** という同一の形でした。終端規則を増やすほど「終端が誤発火する帯域」も増え、そこで header 判定が生き返ります。

memory の `feedback_root_cause_after_n_retries` は「同じ workaround を 3 回適用したら停止して root cause を読み直す」と定めています。しかし実際には **4 サイクル目まで走りました**。守れなかった理由は、毎回「前回とは違う設計」に見えたことです。

**「同じ形」の判定基準**（今回の事例から抽出）:

- **修正の方向が同じなら、実装が違っても同じ形**である。設計 1〜3 はすべて「終端判定を足す」方向だった
- **欠陥の発生条件が同じ層なら同じ形**である。D1〜D4 はすべて「終端が誤って発火 / 発火しない帯域」で起きた
- 判定は**設計ごとではなくサイクルごと**に行う。「前回と違う実装だから新しい試み」と数えると永久に止まらない

### 2. 敵対的レビュー 2 本が、観点は直交していたのに同じ盲点を持った

**影響: #2248 が潜在バグを持ち込んだまま main にマージされ、#2251 で 1 サイクルを消費した。**

#2248 では敵対的レビューを 2 本入れ、攻撃対象も変えていました。しかし**両方とも temp repo で `git diff` を作る同じ手癖**で fixture を組んでおり、`diff --git` を持たない diff の帯域を見落としています。その結果、`collectAddedLineHints` が非 git diff で 2 本目以降のファイルを落とす欠陥を main に入れてしまいました（dead export のためユーザー影響はゼロ）。

**観点を直交させるだけでは足りません。入力の分布まで揃ってしまうと、同じ盲点が残ります。**

さらに一段深い層がありました。D2（overstate）と D3（understate）は **「宣言と実体が食い違う手書き patch」** という帯域です。`git diff` は宣言と実体を必ず一致させるため、この帯域は実コミット diff をいくら流しても出てきません。

**帯域の一部はリポジトリ内の既存 fixture に実在します。** `tests/heuristic-review.test.mjs` の手書き diff を実測すると **overstate（宣言 > 実体）が多数**ありました。ただし **D3 の条件である加算側 understate（宣言 < 実体）は 0 件**です。既存 fixture が覆うのは D2 側の帯域だけでした。**D3 側は fixture にも存在せず、テストも書かれていません。**

## 3 セッション並行での共有生成物の取り合い

このウェーブ固有の運用知見として記録する。

**起きたこと**: `runners/github-action/dist/**` を 3 系統が取り合いました。うち 1 系統（PR #2259）は `ListAgents` に river-review の作業セッションとして現れません。こちらとピアのどちらからも **接触できませんでした**。

**落ち着いた運用**:

1. **dist 衝突はブロッカーではなく CI 1 周のコスト**です（手で解かず再生成して解決するため）。この認識を共有できた時点で、厳密な順序合意は不要になりました
2. **release PR は先に閉じる**（open の間に他をマージすると作り直される）
3. その後は**先着順**。マージした人が他系統へ連絡する
4. 後発は `git merge origin/main` → `npm run build:action` で **dist を再生成**する。`index.mjs.map` を手で解決しない

**連絡の取れない系統がいても破綻しなかった理由**は 1 にあります。順序を決められなくても、衝突は再生成で解けるため、待ち時間そのものは事故になりません。

**残る課題**: 全セッションが同一の `gh` アカウント（`s977043`）を使うため、**PR の author で系統を識別できない**。今回は PR の変更ファイルから推測した。
