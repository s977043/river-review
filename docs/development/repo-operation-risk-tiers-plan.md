## P2.5: 段階 2 への移行（ユーザーの外部作業を含む）

| 項目              | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 前提条件          | P2 の合格条件を満たしていること。ADR の段階 2 の前提条件 1〜7 を満たしていること                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 外部作業（人間）  | エージェント専用の GitHub App または machine user を作る。権限は contents / pull-requests の write までとする。admin・変数・protection・ruleset・`workflows` の権限は与えない。エージェントの実行環境を、人間の認証情報を持たない環境（クラウド routine、または専用の OS ユーザーやコンテナ）へ移す。`gh-account-guard.sh` を見直す                                                                                                                                                                                                                                                              |
| tier-gate の拡張  | cliff / hill の判定に、reviews API による人間の approve の確認を加える。条件は、人間アカウントであること、`state: APPROVED`、`commit_id` が現在の head SHA と一致すること、その後に `CHANGES_REQUESTED` や dismiss が無いこと。満たさなければ pending（人間待ち）とする                                                                                                                                                                                                                                                                                                                          |
| 承認後の再評価    | **未決設計**。`pull_request_review` は PR head 側の定義で実行されるため、判定 workflow のトリガーにしない（ADR の不変条件 1）。案: 権限なしの stub workflow が `pull_request_review` を受けて `repository_dispatch` または `workflow_run` を発火し、base 側で定義した評価器を起動する。評価器は stub から渡された値を信用せず、PR 番号から全入力を取り直す。採否は人間が決め、sandbox で実証してから実装する                                                                                                                                                                                     |
| protection の順序 | `docs/governance.md:72-85`（1.2 節）は必須チェックの context 名を変える場合の手順であり、ここでは**順序の考え方だけを流用する**。1) `tier-gate` が base 側で動き、全 PR（新規・既存の open PR・merge_group）に check を報告していることを確認する。2) branch protection の required status checks に `tier-gate` を登録し、判定 workflow を実行する App の `app_id` で固定する（`docs/governance.md:78-83`）。required reviews は使わない。`enforce_admins: true` は維持する。3) `gh api repos/OWNER/REPO/rulesets` で ruleset を確認し、必須チェックを持つなら揃える（`docs/governance.md:81`） |
| 復旧手順          | 登録後に `tier-gate` が報告されず、PR が `N of N required checks are expected` で止まった場合: 1) 人間が `tier-gate` を required から外す。2) 原因（workflow の無効化、トリガーの不足、context 名の不一致）を直す。3) 手順 1 から登録をやり直す                                                                                                                                                                                                                                                                                                                                                  |
| 承認区分          | Always ask。protection の変更は人間だけが行う                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 合格条件          | sandbox で次を実走して確かめる: エージェント環境から人間のトークンを取得できない（`gh auth token`、キーチェーン、環境変数、`~/.config/gh` のいずれからも取れない）。エージェントの認証では崖・丘 PR をマージできない。人間が head SHA に approve するとマージできる。approve の後に push すると再び pending になる。field PR は approve なしで pass する。ブランチ上の workflow から投稿した偽の `tier-gate` では必須チェックを満たせない。`AUTONOMY_ENABLED` を外すと field PR も pending になる                                                                                                |
| 運用ロールバック  | protection から `tier-gate` を外す（人間）。手順は登録の逆順                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

| 実行主体         | 【提案】`/schedule`（クラウド routine）。権限は最小とし、P2.5 のエージェント用アカウントだけを使う。**リポジトリの `.claude/hooks/` がクラウド実行で効くかは未確認なので、効く前提にしない**。停止は `AUTONOMY_ENABLED` と必須チェック `tier-gate` で保証する                                                                                                                                                                                                                                                                                                                                                                                                            |
| 流れ             | backlog を 1 件選ぶ → 計画 → 3 ループのレビュー（既存の `/range-review` を再利用）→ PR → 原っぱのみ `gh pr merge --auto` → range review → carry-over の更新。人間に届くのは digest と崖・丘の判断依頼だけ                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 既存経路         | `gh pr merge --auto` の既存使用は無い（`.claude/worktrees` と `node_modules` を除外して `.github` `.claude` `scripts` `docs` `src` を grep し、該当 0 件）。auto-merge は新設になる。既存のマージ経路は、人間が起動する `scripts/merge-chain.sh:358`                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 実行の安全性     | 同一ジョブの重複起動を防ぐ（routine 側のロック）。timeout や部分失敗のときは、PR を draft に戻して停止する。auto-merge は `tier-gate` の判定時の head SHA を前提に設定する。監査 artifact（全 finding、coverage、失敗、provenance）を PR コメントと run-record に残す。digest は要約であって SSoT ではない（ADR-012 D2 `:62-80`、D3 `:82-94`）                                                                                                                                                                                                                                                                                                                           |
| dry-run          | 2 週間、マージせずに digest だけを出す                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| dry-run 合格基準 | 原っぱと判定された PR が 10 件以上あること。人間の事後判定で「原っぱにすべきでなかった」が 0 件。原っぱ PR の CI 初回失敗率が 20% 以下。重複起動 0 回。キルスイッチの OFF から次回起動が止まるまで 1 回以内                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 承認区分         | auto-merge の有効化と branch protection の変更は Always ask（`CLAUDE.md:15`）。routine の追加は ADR-016 で崖                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 停止条件         | 原っぱ起因の main 赤（P4 の帰属規則で判定）が 1 回でも出たら、`AUTONOMY_ENABLED` を外して停止する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 運用ロールバック | 1) routine を無効化する（次回起動を止める）。2) 実行中の routine は完了を待つか cancel する。3) `AUTONOMY_ENABLED` を削除する（`tier-gate` が全 PR を cliff として判定し、待機中の auto-merge も止まる）。4) open PR の auto-merge をまとめて解除する。`gh pr list --state open --json number,autoMergeRequest --jq '.[] \| select(.autoMergeRequest != null) \| .number'` で列挙し、各 PR に `gh pr merge <N> --disable-auto` を実行する。5) 解除に失敗した PR があれば、PR 番号を添えて人間に通知する（手順 3 により、解除できなくても人間の approve なしにはマージされない）。6) マージ済みの問題 PR は、通常の revert PR で戻す（force-push しない。`AGENTS.md:48`） |

| 運用ロールバック  | 許可リストから項目を外す（崖の変更）                                                                                                                                                                                                                                                               |
